# Interoperability Stages: current-view inventory (Step 2)

This inventory records the **DFU Severity Score KO** Stages lesson as it appeared at Step 2, before the Step 3 terminology change. Its historical “Meaning” and “Data Objects” entries below are not the current control labels; those are now **Semantics** and **Data object profiles**. It follows the [teaching contract](INTEROPERABILITY-STAGES-TEACHING-CONTRACT.md). It does not redefine the three dimensions or change the SWA. “Published” below means the KO's `auxiliary/aux-extra-metadata/interoperability.metadata.txt`; “exercise” means files under `auxiliary/aux-interoperability-exercise/`; “simulation” means SWA projection, validation, and fixture replay. The same teaching files are embedded in the server and standalone editions.

## Published record versus Metadata Rig filters

The published Turtle root describes the executable capability with `schema:object` (completed questionnaire response) and `schema:result` (Wagner result), a `dcterms:conformsTo` node pointing to named input/output profiles, and a `schema:potentialAction` with `schema:target`, `schema:object`, and `schema:result`. These are the published anchors for the three dimensions. The Metadata Rig's **Object References** filter selects the root object/result and profile links; **Specified Interface** selects the potential-action and target links. They are **different filtered slices of one record**, not alternative names for two Stages dimensions. The current Stages dialog shows the exercise simulation branch instead of the published `InteroperabilityBoundaryPanel`, so this connection is not visible there.

## Unsupported or potentially misleading implications to address later

1. **Live execution:** “Try Interface,” an animated operation, and delivered output can look like a call into the KO. The implementation is not invoked; the SWA replays supplied fixtures and cases. The “Simulation” tag and some explanatory sentences help, but the visual result still warrants an explicit source distinction in a redesigned view.
2. **A single unchanged example across all stages:** State 0/1 use raw output `{ "output1": "2" }`; State 2/3 use a structured expected result. The current State 2 sentence says “the same input and output are progressively annotated.” The *input example* is effectively the same, but the output representation changes. The sentence overstates what is held constant.
3. **Published detail:** Stage 1 field meanings, Stage 2 field constraints, and Stage 3 signature/bindings/error cases are supplied by exercise artifacts. The published Turtle links concepts, profiles, and action, but does not itself contain those details. A view that presents everything as “published metadata” would overclaim.
4. **Full conformance:** The SWA's conformance badge is based on its own limited checker over profile properties. It should not imply exhaustive validation of all possible inputs or a certified interoperability boundary.
5. **Actual KO errors:** Invalid input, misplaced argument, and operation failure are scripted cases. No source establishes that the KO implementation actually emits those exact errors or follows those Promise rejection paths.
6. **Example error's allowed values:** The invalid-input teaching case shows `0`, `1`, and `X` as accepted correction choices, whereas the full input profile also permits `"i"` and numeric `0`/`1`. In context the subset may be intentional, but “This input understands” could be read as the complete allowed set.
7. **Fallback declarations:** The Stage 3 focus panel has SWA defaults for missing parameter, location, position, requiredness, passing convention, and completion fields. The current KO kit supplies these values, but in a general-purpose Stages view a missing field must not become an apparent interface declaration merely because the UI supplied a default.

This completes the source inventory for Step 2. It identifies what the present view shows and what it only simulates; it does **not** implement the later terminology, layout, or source-navigation changes.
